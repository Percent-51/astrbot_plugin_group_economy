# 设计说明

这份文档解释**为什么这么写**。代码里已经有逐行注释，但那些是战术；这里讲的是战略：有哪些互斥的选择，我为什么选了这一边。

---

## 一、货币：双轨制是地基

### 问题

一个群聊经济体只有两种钱：

1. **系统凭空发出来的钱**（签到、答题奖励、BOSS 分红）
2. **群友之间换手的钱**（红包、赔付、存贷、转账）

如果都走同一个入口加币，会同时坏两件事：

- 群友互发红包 → 双方都算「今天赚了」→ 顶破每日上限 → 上限形同虚设
- 彩票头奖 888 → 被上限削成 300 → 「我明明中了头奖只有 300」

### 方案

```python
earn(amount)          # 系统发钱：受每日上限截断，计入 earned
add(amount)           # 群内转移：零和，不计入
spend(amount)         # 消费：余额不足直接失败，不做半扣
debit(amount)         # 挪进内部账本（存钱/还款）：不算支出
credit(amount)        # 从账本挪回现金（取款/放款）：不算收入
force_deduct(amount)  # 强制划扣（催收）：扣到 0 为止
```

关键在最后两个：**存钱不是支出，取钱不是收入**。如果存 500 记成「花了 500」，玩家的「总支出」会虚高一大截，排行榜和统计全不可信。

### 副作用与接受理由

`earn()` 被截断时**不补发**。也就是说今天到上限了，存款利息就直接蒸发。

这看起来像 bug，其实是刻意的：补发就意味着「先把今天的上限用光，再去存一大笔，明天领超额利息」，等于开了条绕过上限的通道。宁可让那点利息消失。

## 二、每日上限到底在管什么

上限（默认 300/人/天）只管一件事：**防止勤奋的人无限印钞**。

它不管：
- 红包（零和）
- 彩票赔付（零和）
- 贷款放款（负债换现金，算进上限的话借 3000 会被截成 300，贷款直接废掉）

一个 10 人的活跃群，理论上限是 3000/天。这个数字不是拍的，是**和消耗端配平过的**，见第四节。

## 三、银行的三条腿

### 存款：给存量资金一个去处

日息 1.5%，按持有时长折算：

```
interest = int(dep × 0.015 × min(elapsed_hours, 48) / 24)
```

**为什么要折算时长**：按天一刀切会出现隔夜套利——23:59 存入、00:01 取出，也吃满一天利息。折算之后，存 10 分钟就只有 10 分钟的利息。

**为什么要 48 小时上限**：这是防灾开关。真实事故是这样的——容器重启后磁盘态回滚，`loan.ts` 退回到起借时刻，`rate` 退回借入时的旧值，下一次结算就会把整个借款周期按旧利率重算一遍，实测让一个用户多付了 1317 堡贝（应付 534，实收 1851）。加了上限之后，同类事故单次损失封顶 ≈ 48 小时利息。

### 信用贷：给「想玩但没钱」的人一个入口

| 档位 | 信用分 | 额度 | 日息 |
|---|---|---|---|
| 家人 | ≥800 | 2000 | 3% |
| 老朋友 | ≥300 | 1200 | 4% |
| 常客 | ≥100 | 800 | 5% |
| 熟客 | ≥20 | 500 | 6% |
| 路人 | ≥0 | 300 | 8% |

额度与利率是原设计，**判定依据换了**：原版挂在一张宿主机器人私有的表上，开源版既拿不到也不该有。这里换成可解释的信用分：

```
新用户 60 ｜ 按时还清 +25 ｜ 逾期后还清 +5 ｜ 逾期一次 −20 ｜ 破产 −60（上限 1000）
```

信用分这个词每个人都懂，不需要读文档就知道「按时还钱能借更多」。

### 三个防套利细节

1. **循环贷不重置期限**。未还清可以继续借，但「本金 + 已计息 + 本次」不得超额度，且期限仍按首笔算。否则反复追加就能把 7 天期无限延长。
2. **追加后利率取高**。首贷免息券（≤300 免息）之后如果追加 2000，整笔按新档位利率算，**包括原来免息那部分**。否则「用免息券借 300 + 追加 2000」就是白嫖。
3. **存续期禁止发红包**。见第五节。

### 高利贷：通胀阀门

```
上限 3000 ｜ 日息 12% 复利 ｜ 3 天期 ｜ 逾期利息×2 ｜ 每群每日放贷池 10000
```

复利**按天滚，不按结算频率滚**：跨天时把已计息并入本金，同一天内反复结算不产生额外利息。否则谁写脚本刷指令谁占便宜。

借 3000 三天：`3000 × 1.12³ ≈ 4214`，多出来的 1214 **凭空消失**（不进任何人口袋）。这是本插件最大的货币销毁口。

逾期后：先扣存款、再扣现金，扣不动就挂在那儿继续滚，同时锁掉发红包。

## 四、通胀预算

所有数字来自真实社群的运行口径（10 人活跃，日均）：

| 项目 | 计算 | 净额 |
|---|---|---|
| 签到 | 50 × 10 人 | **+500** |
| 猜猜猜 | 80 × 约 5 次答对 | **+400** |
| 故事接龙 | 3 × 约 30 句 | **+90** |
| 存款利息 | 约 3000 存量 × 1.5% | **+45** |
| 彩票底池 | 全场注额 × 20% | **+100** |
| — | — | — |
| 刮刮乐 | 净回收 2.92/张 × 20 张 | **−58** |
| 小剧场 | 50 × 2 场 | **−100** |
| 猜词提示 | 20 × 5 次 | **−100** |
| 幸运号抽水 | 注额 5% | **−50** |
| 高利贷利息销毁 | 约 1 笔/天 | **−1214** |
| **合计** | | **≈ −390** |

结论是**轻微通缩**。这是有意的：群聊经济最难的不是防通胀，是防「没人玩」。轻微通缩会让币越来越难赚，反而提高参与动机。

如果实际跑起来发现币不够花（表现为没人敢下注），正确的调节顺序是：先降高利贷日息 → 再提每日上限 → 最后才动彩票赔率。**别动彩票赔率**，那是唯一一个玩家能自己算出期望的地方，动了会被发现。

## 五、那道「套现锁」

`Bank.locked()` 返回非空时，发包会被拒绝：

```
借钱 → 发红包给同伙 → 同伙领走 → 贷款悬空 → 换个号继续
```

这不是财务计算，是防作弊。同理，原版还锁了「兑换实物」这类出口，本仓库没有这些功能，所以只保留了红包这一处。

**这条锁的位置很关键**：它不在红包模块里判断「用户有没有贷款」，而是银行主动暴露 `locked()`，由调用方来问。这样将来加转账、打赏、商城，都只需要加一行检查，而不用把银行的状态判断复制四遍。

## 六、存档与并发

### 单文件 JSON + 原子写

```
写 .tmp → flush → fsync → os.replace()
```

直接覆写时进程被杀会留下半个坏文件，整群存档一次性报废。`os.replace` 在同一文件系统内是原子的（POSIX 和 Windows 都是）。

读取时按 `utf-8-sig → utf-8 → gbk → latin-1` 依次尝试。某些平台导出的 JSON 带 BOM，`json.load` 会抛 `Unexpected UTF-8 BOM`，表现是**插件启动即崩**——这种问题在用户那里排查成本极高，不如一开始就兜住。

### 一把协程锁，所有读-改-写串行

```python
async with store.transaction():   # 拿锁 → 改 → 落盘
    ...
```

`save()` 内部不拿锁，由上下文保证互斥，否则会自己等自己。

### 懒结算

原版有一堆后台任务：定时开奖、定时结算、定时催债、定时催促。开源版**全部去掉**，改成「谁来找我，就先把账算清」：

| 原版 | 现在 |
|---|---|
| 调度器每小时结算利息 | 签到 / 打开银行时结算 |
| 到点自动开奖 + 播报 | 有人查盘口或下注时开奖，公告跟着他的回执发 |
| 回合限时，超时引爆 | 空转 30 分钟自动作废并退款 |
| 定时催债 | 逾期者下次操作时播报 |

好处：不需要任何后台任务，容器重启不会漏跑，也不会重复跑。
代价：没人碰的期次不出结果。而没人玩的期次本来也没什么可开的。

## 七、兼容性决策

**没有第三方依赖**。不引 `pydantic`、不引 `aiohttp`、不引 `orjson`。插件跑在别人的容器里，多一个依赖就多一个装不上的理由。

**LLM 是可选依赖**。海龟汤和小剧场需要模型，其余全部离线可跑。`make_caller()` 拿不到 provider 就返回 `None`，调用方走降级文案并**明确告诉用户原因**（「这台机器没配模型，只能揭晓」），而不是静默失败。装了没反应比说了不能用更劝退。

**老存档必须能读**。字段缺失一律「取不到就建默认值」，而不是抛异常。三处专门处理：
- `bank.loan` 早期写成 `{}` 而不是 `None`，`isinstance(x, dict)` 会把它当成有效贷款，结算时往上写 `ts`，账户里就挂一笔 0 元贷款
- `bank.coupon` 存成 `1/0`，需要转布尔，否则「用掉了」会被判成还有
- `credit` 字段不存在时按 60 起步

## 八、数值表

### 刮刮乐

| 档位 | 概率 | 奖金 |
|---|---|---|
| 谢谢惠顾 | 36% | 0 |
| 安慰奖 | 25% | 12 |
| 小奖 | 20% | 50 |
| 中奖 | 12% | 100 |
| 大奖 | 6% | 220 |
| 头奖 | 1% | 888 |

期望返还 `0.25×12 + 0.20×50 + 0.12×100 + 0.06×220 + 0.01×888 = 47.08`，售价 50，**RTP = 94.16%**。

测试里直接跑 20000 张验证这个数（容差 ±3%）。这不是形式主义——赔率表被谁手滑改一个数字，没有这个断言就永远发现不了。

### 幸运号

```
彩池 = 全场注额 × 95% + 底池
底池 = min(全场注额 × 20%, 2000)
赢家按各自注额占比瓜分
```

倍率是活的：押爆热门会倒挂（开中也可能回不满本）。这是刻意的——它让「跟风押」变成负期望。

### 炸弹

```
踩雷者已投入（底注 + 猜数费）全部没收
  → 90% 平分给幸存者
  → 10% 销毁
幸存者自身投入原样退回
```

分账守恒由测试断言：`(幸存者收益 + 踩雷者亏损) == -(没收额 - 分给幸存者的额)`。

## 九、如果重来会改什么

- **按群分锁**。现在所有群共用一把存档锁，小剧场生成时（几秒）其他群的操作会排队。正确做法是每个群一把锁 + 全局落盘队列。
- **彩票换成事件驱动**。现在的懒结算足够用，但如果要做「押注期间实时倍率提醒」，还是需要一个轻调度器。
- **题库拆成可热更新**。现在改题库要重启，改成按 mtime 自动重载只需十几行。
- **信用分改成滑动窗口**。现在是累加计数，老用户一旦爬满 1000 就不会再降档，长期会失去约束力。
